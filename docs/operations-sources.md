# Operations metrics sources

The VP operations database is data/operations.sqlite3, which Git ignores. The file is mode 0600. The authenticated API is GET /api/ops-metrics; the local CLI is ./opsctl summary. Every record retains an observation time and source or evidence reference. A source outage is unavailable, never zero.

| Measure | Source and cadence | What it means | Limit |
| --- | --- | --- | --- |
| Pane staffing | Dunking Sheep panes, sampled each minute | Process presence by locally assigned role and reported state | Working, blocked, and done are terminal states, not verified productive work. |
| Recent PR state | Read-only GitHub PR list, at most every five minutes | Visible recent review and merge events | The last 100 PRs are a queue sample, not a whole-game completion denominator. Local unpublished work is absent. |
| VP message volume | Local VP messages SQLite, sampled each minute | Counts by channel and author role | Does not cover other conversations and stores no message text in the operations database. |
| Dunking Sheep flow | Aggregate metrics API, one-hour window at most every five minutes after daemon rollout | Message queue and handling counts with interval timestamps | Currently unavailable until the running daemon supports schema version 1. No message bodies, subjects, filenames, or account emails are accepted. |
| Weekly quota | VP direct /status observation, manually entered with provider, pane, time, reset, and evidence | Separate Codex and Claude percentages for the observed account | Stale readings retain their percentage and age. An unobserved provider shows no reading. Panes sharing an account must be grouped by reset cohort. Burn is calculated only within one provider, cohort, and reset after two direct readings at least 30 minutes apart. |
| Local progress | PM-reviewed goal observations with evidence reference | Credited strict full-C functions and measured local queues | Provisional parity gates and queue starts do not add strict full-C credit. |
| Published function coverage | Both accounting JSON files pinned to one GitHub main commit, sampled at most every five minutes | Strict full-C and verified identity counts divided by the PM-reviewed function ceiling | Percentages are minimum function coverage, not whole-game completion. Both files must describe the same original binaries. |
| Overall progress | PM-reviewed goal observations with evidence reference | Playable C demo gate and verified whole-game denominator | The playable demo is blocked until a same-state DOS/C frame; no verified whole-game denominator exists. |
| Fixed subscriptions | Owner-reported amounts entered privately with ./opsctl subscription | Latest monthly amount by provider and their sum | Excludes unknown taxes, add-ons, and usage charges; no amount is hardcoded in tracked source. |
| OpenCode model cost | Read-only aggregate of local OpenCode session costs in ~/.local/share/opencode/opencode.db, read on each summary request | All-time and Los Angeles calendar-month estimates matching the source used by `opencode stats` | Covers all local OpenCode projects. This is a model-cost estimate, not confirmed billed overage; do not add it to the $10 Go subscription. Missing or unreadable data is unavailable. |
| Host health | Latest private `host_watch.py` timer sample, read on each summary request | `/tmp` use/free space/inodes, load, CPU pressure, process and zombie counts, threshold state, and observation age | A sample older than three minutes is marked stale. Counts do not identify which process or file is abandoned; inspect before cleanup. |
| Fixed price per calendar hour | Latest owner-reported monthly fixed subscription sum divided by calendar hours in the current month | Subscription allocation per elapsed calendar hour | Not metered usage cost or cost per productive coder hour. |
| Function coverage speed | Change in published PM-reviewed strict full-C count divided by actual hours between comparable snapshots, at least one hour and at most 24 hours apart; percentage points also divide by the same reviewed bound | Reviewed function progress per hour | Unavailable until two comparable observations exist. PR merges, starts and provisional parity add no credit. |
| Model trials | Manually recorded pane, model, reasoning effort, hypothesis, dated start/end, and evidence | Distinct authored function outputs per trial; latest exact-head accepted bodies per completed trial hour by model and effort | Later repairs retain the original trial's authored output but do not inherit its acceptance. Trial hours exclude later PM review; tokens and metered dollars remain unknown unless separately sourced. A provisional authored body adds no accepted credit. |
| C body events | Exact local or published source head and evidence, with named reviewer for acceptance | Latest status per original function by event occurrence time, then insertion ID for ties | A late historical import cannot reverse a newer acceptance. This local trial ledger does not replace PM-reviewed published strict-C accounting. |
| Usage money (billed) | No billing source connected | Unknown | Pane activity and quota percentage cannot be converted to token or marginal dollar cost. |
| Reply speed (every agent) | `tools/reply_latency.py` in the ops snapshot: Dunking Sheep `inbox.db`, one row per pane (pane id recorded on the message, else the pane named in its mailbox label) | For messages that arrived in 24 h: arrival to the agent's first read or ack, nearest-rank p50/p90/max and count; unhandled in 24 h; silent = open messages (any age) older than 3x the agent's own p50, with the oldest id. Ranked by p50 among agents with at least 5 handled messages whose pane is open; the rest listed below | Computed from message timestamps, no model involved. A read is seeing the message, not finishing the work. Replies are not used: messages carry no thread id. An agent with nothing handled shows "no messages handled in window", never a perfect score, and all its open mail counts as silent. |
| Cost per agent | `tools/agent_costs.py` in the ops snapshot (every 10 min): Claude JSONL under ~/.claude/projects, Codex rollouts under ~/.codex/sessions, pi sessions under ~/.pi/agent/sessions, OpenCode `message` rows. Read incrementally from a byte-offset cache beside the snapshot | Tokens per harness per checkout directory for the rolling 24 h and the Los Angeles calendar month; dollars only where the harness itself recorded them (pi, OpenCode) | A row is a harness in a checkout, not a pane: panes sharing a checkout share a row. Claude and Codex dollars are null with the reason "tokens only". Recorded dollars are list-price estimates, not bills. Tokens include cache reads. Claude repeats a record per content block; each message ID counts once. Codex counts are deltas of its cumulative counter; a drop is a reset. |
| Free-model leaderboard | `tools/free_leaderboard.py` in the ops snapshot: `data/free_runs/*/verdict.txt` and `run.log` (one attempt per body; a re-run overwrites it) and `data/bakeoff/*/results.tsv` (one row per attempt) | Per model: verified bytes, verified decodes (distinct bodies whose dumped bytes matched GAME.OVR), runs, empty, no dump, wrong bytes, unchecked, last seen; tier free / subscription (OpenCode Go) / metered; ranked by verified bytes | A verified decode means the bytes matched the game file. It does not mean the model's interpretation was right, and it is not a credit. Accepted and assisted lines are null ("no per-line attribution exists yet") until merged PRs or the credit table name the model that seeded a body. |
| Free-model work volume | Same scan: pi and OpenCode sessions whose model id ends `-free` or `:free`, or is `big-pickle`; outcomes from the dunkingsheep `docs/FREE_MODEL_LEDGER.md` table | Runs (sessions) per free model for 24 h and the month; reviewed outcomes per model: accepted, after rework, rejected, failed | A run is a session that called a free model, not useful work. Only ledger rows are reviewed; a run without a ledger row is unreviewed, not accepted. Runs and ledger rows are not joined because their model names differ by provider prefix. Headless runs that keep no session file are not counted. |
| Overall usage panel | Latest `provider_usage_snapshots` row (from `dunkingsheep usage`, stored by the metrics timer) and the latest owner-reported `subscription_costs` per provider | Each provider's own windows as percent used with reset times; Claude extra usage billed beyond the plan; fixed monthly subscriptions in their own list | Percentages and dollars are different units and are never summed. The pi reading is a local session estimate, not a quota. Extra usage is converted with the provider's `decimal_places`. |
| Current dunks | `tools/delivery_stats.py` in the ops snapshot (every 10 min): `dunkingsheep --json list` (daemon); `dunks.json` when the daemon does not answer, with the reason in the source line | Every dunk the daemon holds, running or not: target pane and label, cadence, state, gates, last and next fire, sent/skipped/held, minutes overdue | Next is the schedule, not a promise: idle-only and hold-while-typing can delay a send. The daemon's countdown text is replaced by the absolute next time. States read from the store are marked derived. |
| Inbox metrics | Dunking Sheep `inbox.db`, read-only | Per mailbox and total: unread (any age), oldest unread in hours, arrivals in 24 h, and the nudge state of those arrivals (delivered / queued / failed / none) | Unread is unopened, not unhandled work. A delivered nudge means the text was submitted to the pane, not that the agent read it. |
| Arrival to delivery | Dunking Sheep `metrics.db`, `message.sent` events in 24 h, `duration_ms` = notice queued to text confirmed submitted; nearest-rank p50/p90/max, total and per mailbox | How long the messenger takes to put a notice in front of an agent | Covers finished sends only. Notices still queued are reported beside it as "still waiting" with their age, because an unfinished stall has no duration. |
| Delivery health | `dunkingsheep --json messages` (daemon queue) and `--json panes`; the `dunks.json` outbox when the daemon does not answer | Every nudge not yet delivered, with its reason: typing, draft, busy claim, stranded, or dead pane (target pane id absent from the live pane list) | The reason words other than dead pane are the daemon's own. A pane id reused by a new agent is live, so a message meant for the old agent is not shown as dead. If the pane list is unreadable, no row can say dead pane, and the panel says the pane list was unreadable. |
| Credited | `tools/credit_stats.py` in the ops snapshot: poolrad-decomp `docs/re/function_accounting_checkpoint.json` (`strict_full_c_originals`) and `docs/re/credit_evidence_kind.csv`, both read at the local main checkout's HEAD commit with `git show`, never the working tree | Reviewed strict C bodies pinned in the checkpoint, the evidence-kind breakdown (a kind that left the table in the last 14 days shows as 0), and the change over 24 h and 7 days from the checkpoint's commit history | Not "runs in the game"; that is Replaced. 815 is a ceiling. The local checkout must be pulled for new acceptances to appear; the panel names the commit. |
| Replaced | poolrad-decomp `docs/re/replaced_bodies.json` (schema `replaced/1`: per body `id`, `proven_at`, `evidence.kind` pixels or arrivals, `evidence.differing`) | Bodies the game executes as our C, counted only with `differing == 0` from an identical run | Null with "not yet collected" until a lane writes the file. `hybrid_status.json`'s "running as our C" is parsed from prose and is not counted. |
| Credited and replaced per day | Timestamped events: every commit that changed the checkpoint (with the count it pinned) and each `proven_at` in the replaced file | Net change per Los Angeles calendar day over 14 days, and the 7-day mean | Commit time is when an acceptance was committed, not merged. A batch publication is one commit (the largest steps are named on the panel). A day before the checkpoint existed is unknown, not zero. |

The collector timer runs once per minute. GitHub and Dunking Sheep polling are throttled to five minutes. Roles are private local assignments entered with ./opsctl lane; the checked-in code contains no actual pane roster. If a source is down, the prior observations remain in the database with their original timestamps.

Enter each new direct quota observation through `./opsctl quota --provider codex|claude --pane PANE --left PERCENT --reset ISO_TIME --observed-at ISO_TIME --evidence SOURCE`. The Operations view refreshes its sourced Codex and Claude quota cards every minute; **Refresh data** fetches them immediately. Do not infer a Claude percentage from a Codex reading or from an owner statement without a dated, account-specific observation.

The private Operations view plots a rolling 24-hour history from
`GET /api/ops-metrics/history` and a seven-day verified strict-C checkpoint
history from `GET /api/ops-metrics/history?hours=168` (allowed range: 1–168 hours):
PM-reviewed strict full-C and verified-identity
observations, actual merge timestamps for the recent visible PR sample, and
working coder pane counts from successful collection runs. Missing samples are
not interpolated. Merge throughput and pane presence are engineering flow
signals, not deployments or verified productivity. Deployment frequency, change
failure rate, and recovery time remain unavailable until deployment and incident
records exist.

The executive C economics panel uses the latest published strict-C count and
working ceiling. The 24-hour credit delta requires a verified observation at
or before the 24-hour boundary, agreement between the latest manual credit
observation and published accounting, and an accounting sample no older than
60 minutes; otherwise it is unavailable. The credit card shows the accounting
sample age so a stale published count cannot appear as a measured zero-credit
day. The chart steps only at dated PM-reviewed credit observations. Its horizontal tail is
the last recorded value, not evidence of zero work in progress.
The C staffing line is a dated PM checkpoint: assigned lanes and authorized
compile/native slots are separate. Neither measures productive lane-hours.

The fixed subscription pool per calendar hour divides owner-reported monthly
subscriptions by hours in the current month. The interactive equal-allocation
figure divides that pool by a user-selected number of modeled C lanes, assuming
the entire pool supports those lanes during every calendar hour. It is a planning allocation, **not**
observed C spend per hour. Actual C spend requires C lane-hours, a billing
allocation, and usage charges. The milestone and cost figures use a selected
new verified functions per week; they are hypothetical scenarios, not an ETA.
The 24-hour signal pairs a comparable net credit count with 24 hours of fixed
pool commitment across all work; the latter is not attributable to C.

Every panel prints its as_of and source and says STALE when the reading is older than 15 minutes (owner #1358). A section missing from the snapshot renders as "Not in this snapshot", never as an empty space.

## Network exposure (an open decision, not a default)

`run.sh` binds the desk to `0.0.0.0` unless `VP_BIND` is set, so every page above, including mailbox names, dunk texts and costs, is reachable from the LAN behind the desk login. The VP rule is loopback only. It is left as it is (2026-10-23) because the owner may need LAN access. Set `VP_BIND=127.0.0.1` in the service environment to change it, and record whoever decides here.

## Hidden projects

Crackdown panels hidden 2026-10-23 at owner request (#1381); data retained; reason: port shelved. The collector still writes every Crackdown field (the project card, cost rows, dunks, mailboxes) and the operations database keeps its history; `web/src/hidden.js` filters the rendering only, and each table says how many rows it hid. Totals and percentiles still include the hidden rows. Delete the entry in `HIDDEN_PROJECTS` to show it again. Because the hide is a rendering switch and collection continues, the "N rows from a hidden project not shown" counts will grow while the port is shelved. That is expected, not an error: it is the history accumulating for when the project comes back.
